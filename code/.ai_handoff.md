# AI handoff — reproducible code architecture

This file is the canonical operating contract for future AI sessions that create or modify Python under `code/`.

## Core reproducibility rule

Scientific logic and experiment orchestration are different things and must stay separate.

```text
controlled data
    ↓
reusable functions/classes
    code/src/visitas_analysis/...
    ↓ imported by
stable experiment / pipeline runner
    code/experiments/<experiment_id>.py
    or an existing canonical runner such as code/src/run_study.py
    ↓
versioned configuration
    code/config/...
    ↓
local generated outputs
    code/outputs/  (ignored by Git)
    ↓ after review
retained aggregate outputs
    analysis/
    ↓
reports/ and papers/
```

**When data are updated, rerun the same stable runner with the updated controlled inputs. Do not rebuild the analysis manually, copy calculations into a notebook, or create a new version-suffixed script.** Git records code history; stable script names record the scientific procedure.

## Before writing any new function

1. Read this file.
2. Search `code/FUNCTION_INDEX.md` by concept, symbol name, and tags.
3. Open only the most relevant existing implementation(s).
4. Reuse or extend an existing function whenever its scientific meaning matches the requested calculation.
5. Create a new function only when no existing symbol implements the same estimand/transformation/test.
6. Put the function in the module that owns the scientific concept; do **not** place reusable scientific logic inside a runner.
7. Add a docstring that states purpose, important inputs/outputs, and scientific caveats when relevant.
8. Add or update tests.
9. Import the function from the stable runner that reproduces the experiment/question.
10. Commit the regenerated `code/FUNCTION_INDEX.md` in the same scientific change. The repository workflow also regenerates it automatically for Python changes.

## Experiment runners

A runner is a **thin, stable, executable scientific recipe**. It imports reusable functions; it should not contain a second implementation of them.

New experiment-specific runners belong under:

`code/experiments/`

Use stable, descriptive names tied to the scientific question, not versions or dates. Examples of valid future names:

- `paper1_ppa_persistence.py`
- `paper2_mu_performance.py`
- `paper3_grading_heterogeneity.py`
- `paper4_degree_help_seeking.py`
- `paper5_longitudinal_trajectories.py`

Do **not** create names such as `paper2_v2.py`, `analysis_final.py`, `experiment_new.py`, or `paper2_2026.py`.

A runner should normally do only these things:

1. load a shared configuration;
2. load/construct the required canonical cohort through reusable functions;
3. call the reusable analysis functions in a fixed order;
4. save outputs to deterministic paths;
5. write enough run metadata to identify configuration/data coverage when practical;
6. exit with an error if required inputs or invariants are not satisfied.

If an estimand changes materially, update the scientific code, tests, protocol, and runner under Git. Do not preserve old methodology by leaving duplicate versioned scripts in the working tree; Git history is the provenance layer.

## Reproducibility contract for each experiment

Every experiment that supports a reported result should eventually have:

- a stable runner path;
- explicit reusable-function imports;
- configuration stored in code/config or explicit runner constants when truly experiment-specific;
- deterministic output paths;
- tests for the scientific helpers it depends on;
- no hard-coded result values copied from prior runs;
- no dependency on a manually executed notebook;
- documented cohort/estimand in `STUDY_PROTOCOL.md` or the relevant methodology document;
- a clear mapping from output files to the report/paper that consumes them.

For stochastic methods, seeds and relevant algorithm settings must be explicit and version-controlled.

## Data-update rule

When a new institutional-data extract arrives:

1. keep the existing experiment runner unchanged unless the schema or scientific specification genuinely changed;
2. update controlled input paths/configuration, not analysis logic, when only the data vintage changed;
3. run tests first;
4. rerun the same stable runner;
5. compare cohort counts, diagnostics, and outputs with the prior retained aggregate results;
6. investigate differences before replacing canonical aggregate outputs;
7. retain the new reviewed aggregate outputs under `analysis/`;
8. update reports/papers from those outputs rather than editing numerical results by hand.

A new data vintage is **not** a reason to create a new function or a new `*_v2.py` runner.

## Scientific-change rule

A code change is scientific if it changes cohort membership, variable construction, estimand, statistical test/model, standard-error calculation, imputation, threshold logic, or any reported numeric result.

For a scientific change:

1. explain the reason in the commit/PR;
2. update tests;
3. update `STUDY_PROTOCOL.md` / relevant methodology documentation;
4. ensure `FUNCTION_INDEX.md` is regenerated;
5. rerun the affected stable experiment runner(s);
6. compare old/new aggregate outputs;
7. update reports/papers only after the canonical outputs are accepted.

Presentation-only code changes may skip scientific reruns when they cannot affect numerical results, but this should be explicit.

## Function index rule

`code/FUNCTION_INDEX.md` is the search surface; this handoff is the architecture/routing surface.

- Do not manually maintain a second list of all functions here.
- Search the function index before opening large source modules.
- If a new function is not discoverable from its name/docstring/tags, improve the docstring or naming rather than adding parallel documentation.
- Run `python scripts/generate_function_index.py` from `code/` to regenerate locally.

## Minimal future-session startup for code work

1. `AI_HANDOFF.md` — global project state;
2. `code/.ai_handoff.md` — this reproducibility contract;
3. `code/FUNCTION_INDEX.md` — locate existing capabilities;
4. `code/STUDY_PROTOCOL.md` and `code/ADMINISTRATIVE_QUESTIONS.md` — scientific definitions;
5. only then open the specific source module/runner that needs modification.

This order is intentional: it minimizes context use and reduces accidental duplication of scientific logic.
