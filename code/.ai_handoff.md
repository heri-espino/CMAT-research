# AI handoff — reusable code and product-local runners

This file is the canonical operating contract for Python/scientific work in CMAT. The full research lifecycle is documented in `../docs/RESEARCH_WORKFLOW.md`; report-layer experimentation rules are in `../reports/AI_HANDOFF.md`.

## Core architecture

Root `code/` is the **single computational authority**. A useful analogy is to treat it as the project's internal scientific library, similar in architectural role to a package such as scikit-learn: reports import and use it, but do not fork or rewrite its implementations. The library may contain highly CMAT-specific functions whenever they define reusable computational behavior.

Reports and papers may own thin execution entry points, but reusable functions remain here.

```text
controlled institutional data
        ↓
code/src/visitas_analysis/
        reusable scientific/build functions
        ↓ imported by
reports/<report_id>/code/<runner>.py
        product-local recipe / experiment
        ↓
reports/<report_id>/
        diagnostics + tables + figures + notes + provenance + report
        ↓ selected into
papers/<paper_id>/
        publication manuscript/results/submission
```

`analysis/shared/` is an auxiliary location for aggregates with genuine cross-report/project-wide value; it is not a mandatory stage in this production chain.

## Non-negotiable boundary

**Do not implement reusable scientific logic inside `reports/` or `papers/`.**

If a report or paper needs a new cohort rule, transformation, estimator, test, model, confidence interval, imputation rule, plotting function, or reusable build helper:

1. search `code/FUNCTION_INDEX.md`;
2. reuse an existing function when scientifically equivalent;
3. otherwise implement the function under `code/src/visitas_analysis/`;
4. add/update tests and documentation;
5. call that function from the owning product-local runner.

The product-local script should be a thin entry point, not a second analysis codebase.

## Where runners belong

Runners are co-located with the product they build.

### Report runner

```text
reports/<report_id>/
├── code/
│   └── <report_id>.py
├── tables/
├── figures/
├── notes/
├── provenance/
└── ...
```

### Paper runner, only if eventually needed

```text
papers/<paper_id>/
├── code/
│   └── <paper_id>.py
├── manuscript/
├── results/
└── ...
```

Paper-local execution must still import root code and/or consume reviewed report outputs. It may not redefine estimands independently.

There is intentionally **no active `code/experiments/` directory**. The old central runner layer was retired because it separated a product's recipe from the product that owns it.

## Canonical methodology-report example

The stable entry point is:

```bash
python reports/methodology_report/code/methodology_report.py --check
```

With controlled data:

```bash
python reports/methodology_report/code/methodology_report.py \
  --materias <academic-file> \
  --asesorias <visits-file>
```

The local script only locates root `code/` and calls `visitas_analysis.reporting.methodology_build.methodology_report_cli`.

The reusable implementation remains under root `code/`:

- `src/visitas_analysis/study/methodology_pipeline.py` — analysis sequence;
- `src/visitas_analysis/study/extended_methodology.py` — methodology-specific analyses;
- `src/visitas_analysis/study/methodology_plots.py` — methodology figures;
- `src/visitas_analysis/reporting/methodology_report.py` — LaTeX table snippets;
- `src/visitas_analysis/reporting/methodology_build.py` — report-build orchestration.

Disposable working outputs for this product live under `reports/methodology_report/build/` and are ignored by Git. Reviewed/staged tables and figures remain inside the report folder.

## Reports and papers in the research process

Treat the repository as a three-stage production system:

```text
CODE
= all reusable computation; how a calculation works

REPORTS
= experiments, diagnostics, robustness, broad research development and brainstorming;
  what we tried, why, in what order, and what we learned

PAPERS
= publication-ready selections from validated report evidence;
  what subset becomes the final scholarly argument
```

Reports may preserve competing analyses, null results, sensitivities, methodological debate and exploratory branches of the scientific argument. A paper should select only the evidence needed for its publication question while preserving traceability back to the report and root code.

If a new idea originates while writing a paper, do not calculate it directly there: return to the relevant report, search/add root-code capability, run and evaluate the analysis in the report, then promote the validated result back downstream.

## Runner-first rule for reproduction

When the user asks to reproduce an existing report/paper/figure set:

1. identify the exact owning product directory;
2. inspect its local runner/reference implementation;
3. search `FUNCTION_INDEX.md` for the functions it needs;
4. restore a missing historical root-code function only when exact reproduction requires it;
5. keep the local runner thin and execute functions in the required order;
6. verify expected tables/figures;
7. stop unless broader refactoring was explicitly requested.

Do not turn a simple reproduction request into a new architecture, provenance system or duplicate pipeline.

## Before writing any new function

1. Read this file.
2. Search `code/FUNCTION_INDEX.md` by concept/name/tags.
3. Open only the relevant implementation(s).
4. Reuse or extend an existing function whenever its scientific meaning matches.
5. Create a new function only when no existing symbol implements the needed calculation.
6. Put it in the module that owns the scientific concept under `code/src/visitas_analysis/`.
7. Add a useful docstring and tests.
8. Import/call it from the owning report/paper runner.
9. Regenerate `code/FUNCTION_INDEX.md`.

## Function locations

Default publication-oriented scientific logic:

`code/src/visitas_analysis/study/`

Important modules:

- `cohort.py` — cleaning, real attempts, visits, cohort construction;
- `outcomes.py` — classroom-relative outcomes and transformations;
- `statistics.py` — inference, confidence intervals and robust comparisons;
- `selection.py` — propensity/selection sensitivity;
- `temporal.py` — temporal/periodicity diagnostics;
- `extended_analysis.py` — exact counts and programme analyses;
- `ppa_progression.py` — MU→Calculus/PPA longitudinal logic;
- `pipeline.py` — broad publication-study orchestration;
- plot modules — figures from computed results.

General/report-compatible analysis helpers:

`code/src/visitas_analysis/analysis/`

Reporting/build helpers:

`code/src/visitas_analysis/reporting/`

Privacy/release helpers should reuse the existing root-code implementations.

## Shared root-code runners

The following remain in root `code/` because they are broad project utilities/pipelines, not one report's atomic recipe:

| Runner | Role |
|---|---|
| `code/src/run_study.py` | broad publication-oriented study pipeline |
| `code/src/run_analysis.py` | general/descriptive analysis pipeline |
| `code/src/generador_figuras_cli.py` | shared figure utility |
| `code/src/create_anonymized_release.py` | privacy/release packaging |
| `code/src/prepare_release_latex.py` | LaTeX release preparation |

Do not move broad shared logic into a product folder merely for symmetry.

## Data-update rule

When a new institutional extract arrives:

1. keep the same product-local runner unless the scientific specification changed;
2. update controlled input paths/configuration;
3. run root-code tests;
4. rerun the report/paper runner;
5. compare cohort counts/diagnostics/outputs;
6. investigate unexpected differences before replacing retained assets;
7. update narrative prose only after outputs are accepted.

A new data vintage is not a reason for `*_v2.py`, a duplicate report folder, or a new implementation.

## Scientific-change rule

A change is scientific if it changes cohort membership, variable construction, estimand, test/model, standard errors, imputation, threshold logic or reported numeric results.

For scientific changes:

1. modify root `code/`;
2. update tests;
3. update `STUDY_PROTOCOL.md`/methodology documentation;
4. regenerate `FUNCTION_INDEX.md`;
5. rerun affected product-local runners;
6. compare outputs;
7. update reports/papers only after acceptance.

## Function index rule

`code/FUNCTION_INDEX.md` indexes the root computational core. Product-local thin runners outside `code/` are intentionally not part of that inventory.

Run:

```bash
python code/scripts/generate_function_index.py
```

after root-code Python changes. GitHub also regenerates the index automatically for changes under `code/**/*.py`.

## Minimal future-session startup

For any numerical/code task:

1. `AI_HANDOFF.md`;
2. `docs/RESEARCH_WORKFLOW.md` when the task changes/extends the research workflow;
3. this file;
4. `code/FUNCTION_INDEX.md`;
5. `code/STUDY_PROTOCOL.md` and `code/ADMINISTRATIVE_QUESTIONS.md`;
6. `reports/AI_HANDOFF.md` for report experiments;
7. the owning `reports/<report_id>/README.md` or `papers/<paper_id>/README.md`;
8. then the specific root-code module and product-local runner.

This ordering keeps the computational core centralized while making each report/paper operationally self-contained. When a durable code/report boundary rule emerges in conversation, update the appropriate handoff rather than relying on conversational memory.
